# PostHog session replay: sensitive rendered-data audit

Date: 2026-08-27

Audit baseline: `main` at `105154b20a`, before the remediation documented
below. The findings tables describe that baseline behavior.

## Remediation implemented with this audit

The accompanying change closes the high-confidence payload gaps without
returning to blanket page-text obfuscation:

- ordinary page text remains recordable;
- native form values remain masked;
- generic `contenteditable` text is selectively masked;
- the shared `CodeMirrorEditor` blocks its complete subtree;
- the portaled `MediaTag` preview blocks its complete subtree; and
- generated playground output blocks its value body.

This covers the trace corrected-output path, dataset item and schema editors,
playground messages/configuration, prompt/evaluator/experiment editors, media
peek portals, and the trace search composer identified in this audit. The
tables remain useful as the render-path inventory and as evidence for why the
shared protection points were chosen.

## Question and conclusion

This audit answers which additional UI surfaces can render customer/user-supplied values now that PostHog recordings retain ordinary page text while suppressing tracing input/output payloads.

The important boundary is that the current configuration masks native form controls and blocks elements carrying `ph-no-capture`, but it does **not** mask arbitrary rendered text. The highest-confidence gaps in the requested areas are:

1. Dataset item input, expected output, and metadata in current, historical, create, and edit views are rendered in `CodeMirrorEditor` without `ph-no-capture`.
2. Playground messages, variables, message placeholders, provider options, tool/schema JSON, and generated output are unprotected.
3. Trace/observation input, output, metadata, status messages, and diff dialogs are mostly protected, but corrected output in the legacy JSON and pretty views is rendered in an unprotected `CodeMirrorEditor`.
4. Media chips can open a portaled hover preview outside an otherwise blocked subtree; the hover preview itself has no `ph-no-capture`.
5. Trace/observation names, trace tags, user/session IDs, score configuration text, and several tool/schema/prompt names are adjacent user-controlled text and remain visible.

## Masking semantics used for this audit

The application enables `maskAllInputs`, registers `ph-no-capture` as the block class, and removes request/response bodies in [`_app.tsx`](../web/src/pages/_app.tsx#L109-L118). PostHog documents that:

- masking happens in the browser before replay data is sent;
- native input types, `textarea`, and `select` are covered by input masking;
- ordinary text is not masked unless a text selector/class is configured; and
- `ph-no-capture` blocks an element and its contents from replay.

See [PostHog: Session replay privacy controls](https://posthog.com/docs/session-replay/privacy).

`CodeMirrorEditor` renders `@uiw/react-codemirror` without a blocking class in [`CodeMirrorEditor.tsx`](../web/src/components/editor/CodeMirrorEditor.tsx#L558-L575). It is a custom content-editable editor, not one of the native input types enumerated by PostHog's input-mask contract. Therefore this report treats CodeMirror content as **unprotected unless a blocked ancestor exists**.

This was also verified against the installed `posthog-js` 1.417.1 recorder in
headless Chromium. With the application's effective `maskAllInputs: true` and
`blockClass: "ph-no-capture"` settings, the emitted replay events contained a
sentinel placed in a `contenteditable` CodeMirror-style element, while
sentinels in a native `input`, native `textarea`, and `ph-no-capture` subtree
were absent (`2` replay events emitted).

After applying the remediation, the same recorder probe included the ordinary
UI-text sentinel but excluded the native-input, native-textarea,
`contenteditable`, and blocked-subtree sentinels (`2` replay events emitted).

Two portal boundaries matter:

- `HoverCardContent` is portaled into the global popover layer in [`hover-card.tsx`](../web/src/components/ui/hover-card.tsx#L43-L63).
- `DialogContent` is portaled through `DialogPortal` in [`dialog.tsx`](../web/src/components/ui/dialog.tsx#L130-L168).

A blocked trigger or ancestor does not automatically protect content moved to either portal; the portaled content needs its own protection.

Status labels below:

- **Blocked** — protected by `ph-no-capture`, directly or through a shared renderer.
- **Native-input masked** — protected only while inside a native `input`, `textarea`, or `select` by `maskAllInputs`.
- **Unprotected** — no applicable PostHog protection was found.
- **Mixed** — the main body is protected but a portal, label, or alternate view is not.

## Priority interpretation

For the stated policy (“do not record tracing input/output values” while retaining useful non-obfuscated recordings), the minimum high-confidence protection set is:

1. Corrected output in legacy/pretty trace views.
2. All dataset item detail/create/edit/history-normal CodeMirror payloads (input, expected output, metadata).
3. Playground message content, variables, placeholder fill-ins, generated output, tool/schema JSON, and provider options.
4. The shared portaled media hover preview.

Names, tags, IDs, score configuration text, prompt/tool/schema names, CSV headers, and schemas are a policy boundary rather than tracing I/O proper. ## Method

This is a static render-path audit of the baseline commit named above,
