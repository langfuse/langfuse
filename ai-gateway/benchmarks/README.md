# AI Gateway benchmarks

A reproducible single-host benchmark for the gateway's streaming Chat Completions
path with telemetry on. It measures the unmodified release image against a mock
OpenAI upstream and reports added latency, time to first token, per-chunk lag,
throughput, burst behavior, memory, CPU, and failure modes.

## What runs

`docker compose` brings up one gateway with production limits (2 vCPU, 4 GiB,
1 GiB memory budget), Langfuse Web and worker for `/resolve` and trace
ingestion, Postgres, ClickHouse, Redis, MinIO, an OpenTelemetry collector that
writes the gateway's own metrics and spans to `results/otel/`, Toxiproxy in
front of Web for resilience runs, and two Rust tools from `tools/`:

- `mock-upstream` serves `POST /v1/chat/completions` as `api.openai.com` on the
  compose network, over TLS signed by a benchmark-only CA that the gateway
  trusts through `SSL_CERT_FILE`. The gateway therefore runs its production
  provider path, including TLS and connection pooling, with no code change. It
  streams a role chunk, `MOCK_CHUNKS` content chunks (default 20) starting
  `MOCK_TTFT_MS` (20) after the request body arrives and spaced
  `MOCK_CHUNK_DELAY_MS` (10) apart, a finish chunk, and a usage chunk.
- `loadgen` sends streaming Chat Completions in a closed loop at a fixed
  concurrency, or as simultaneous bursts. The request body is a synthetic
  coding-agent turn (system prompt, 12 tool schemas, earlier tool calls with
  file reads, grep and test output) generated by `payload/generate.py`, about
  100 KiB by default. It contains no customer data.

The mock stamps its own clock into every chunk: the `id` carries when the request
headers and body reached it, and `system_fingerprint` carries when that chunk was
written. All containers share the host clock, so the load generator computes,
per request:

| Metric               | Meaning                                                                                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pre_upstream_ms`    | Client send → request headers at the mock. Through the gateway this covers the client upload, buffering the body, `/resolve`, telemetry setup, and the upstream connection. Added latency is this minus the same value sent directly to the mock. |
| `ttfb_ms`, `ttft_ms` | Client send → response headers, and → first non-empty content delta.                                                                                                                                                                              |
| `chunk_lag_ms`       | Mock wrote a chunk → client parsed it: per-chunk forwarding cost.                                                                                                                                                                                 |
| `chunk_gap_ms`       | Gap between consecutive content chunks at the client.                                                                                                                                                                                             |
| `total_ms`           | Client send → stream end.                                                                                                                                                                                                                         |

Errors are counted by HTTP status, transport failure, timeout, and incomplete
streams. `scripts/sample_cgroup.py` samples the gateway, Web, and mock cgroups
(memory, anonymous memory, CPU) every 250 ms during each case.

CPU sets keep the components apart on an 8 vCPU host: gateway 0-1, mock 2-3,
load generator 4-5, everything else 6-7. Change them with `BENCH_CPUSET_*` on
other hosts.

## Run it

```bash
cd ai-gateway/benchmarks
bash scripts/setup.sh                      # CA, mock certificate, .env secrets, payload
docker compose build                       # gateway image, tools, Web and worker images
# Five Web replicas, like a scaled production control plane (see below)
export COMPOSE_FILE=docker-compose.yml:docker-compose.scaled-web.yml BENCH_CPUSET_LOADGEN=2-3
docker compose up -d --wait
docker compose exec -T -w /app/worker langfuse-worker node bench-seed.cjs
scripts/run.sh                             # every scenario; or e.g. `scripts/run.sh sweep burst`
python3 scripts/analyze.py --charts results/<run>/charts results/<run>
```

Building Web and worker from source takes a while. To reuse images you already
have, set `BENCH_WEB_IMAGE` and `BENCH_WORKER_IMAGE`; `BENCH_GATEWAY_IMAGE`
selects the gateway image under test. Pass two run directories to `analyze.py`
to overlay them, e.g. two gateway builds.

The seed (`seed/seed.cjs`, run inside the worker container) creates one
organization, one ingestion project, an OpenAI connection with a placeholder
credential, and the gateway key `sk-lf-gateway-bench`. It is idempotent; set
`BENCH_INGESTION_MODE=FULL` to switch the project from the default `USAGE`
telemetry.

## Scenarios

| Scenario    | What it does                                                                                                                                       |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sweep`     | Direct to mock, then through the gateway, at `BENCH_LEVELS` (1 10 50 100 250 500 1000) for `BENCH_DURATION` seconds (30) after `BENCH_WARMUP` (5). |
| `burst`     | `BENCH_BURSTS` (250 500 1000) requests released at once, `BENCH_BURST_ROUNDS` (5) times, direct and through the gateway.                           |
| `ingestion` | `USAGE` vs `FULL` telemetry at `BENCH_COMPARE_LEVELS` (50 250).                                                                                    |
| `cache`     | Web's resolve cache off vs on at `BENCH_COMPARE_LEVELS`.                                                                                           |
| `web-slow`  | Gateway → Web through Toxiproxy, without and with `BENCH_WEB_LATENCY_MS` (250) added.                                                              |
| `web-down`  | Web paused for `BENCH_WEB_DOWN_SECONDS` (10) in the middle of a run.                                                                               |
| `budget`    | `BENCH_BUDGET_CONCURRENCY` (1000) clients against a `BENCH_SMALL_BUDGET_BYTES` (256 MiB) budget: admission control should answer 503 quickly.      |
| `headroom`  | The same clients with a `BENCH_LARGE_BUDGET_BYTES` (3 GiB) budget, to see the gateway without admission limits.                                    |

`scripts/spans.py results/<run>` splits the gateway's own sampled spans per
case into gateway self time, `/resolve`, body read, telemetry capture, and
upstream headers, which separates gateway cost from Web cost.

The gateway calls Web's `/resolve` on every request and assumes Web is scaled
to keep up, as it is in production. `docker-compose.scaled-web.yml` runs
`BENCH_WEB_REPLICAS` (5) Web replicas on CPUs 4-7, with the mock and load
generator sharing CPUs 2-3 (`BENCH_CPUSET_LOADGEN=2-3`). Without the overlay, one
Web container on the shared infra CPUs saturates first and the run measures Web
rather than the gateway. Report the replica count with every number. To find
the gateway's CPU ceiling rather than the admission budget, add a larger
`BENCH_MEMORY_BUDGET_BYTES` and `BENCH_SKIP_DIRECT=1` to reuse an earlier direct
baseline.

Other knobs: `BENCH_PAYLOAD_BYTES` (rerun `setup.sh`), `MOCK_*` on the
`mock-upstream` service, `BENCH_GATEWAY_CPUS`, `BENCH_GATEWAY_MEMORY`,
`BENCH_MEMORY_BUDGET_BYTES`, `BENCH_GATEWAY_LOG_LEVEL` (info), and
`BENCH_TRACE_SAMPLE_RATIO` (0.02) for the gateway's own OTel spans.

## Limits

- Everything shares one host. CPU sets prevent most contention, but memory
  bandwidth, the kernel network stack, and the Docker bridge are shared, and
  numbers move a few percent between runs.
- The mock is instantaneous apart from its fixed delays, so upstream variance is
  absent and pooling behaves better than against a real provider over the
  internet.
- Every request resolves through Web. Even with five replicas, Web shares four
  cores with the worker and datastores, so at high concurrency this measures the
  gateway together with its control plane, not the gateway in isolation.
- Telemetry is uploaded to Web's ingestion endpoint on the same host. A slow or
  failing ingestion path costs memory in the gateway's telemetry buffer, which
  this does not stress beyond what the scenarios above produce.
